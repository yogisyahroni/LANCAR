## Scope Implemented

Implemented a server-authoritative handoff proof system in `order-service`:

- **Proof requirement matrix** — `proof_requirements` table seeded with 14 canonical rows (package_on_demand, food, tambal_ban, towing × pickup/delivering/delivered/loading/unloading × photo/otp/qr/signature). Requirement is data-driven, not hardcoded.
- **One-time verification tokens** — `IssueProofToken` generates a 6-digit OTP (or alphanumeric/QR format), stores only the HMAC-SHA256 hash + per-token salt, binds token to order + actor + stage + service_category + expiry + max_attempts. Unique partial index on `(order_id, stage) WHERE used_at IS NULL` prevents duplicate unconsumed token per order+stage.
- **Token verification** — `VerifyToken` enforces: token exists, not expired, actor matches, OTP hash verified via `crypto/subtle.ConstantTimeCompare`, attempt counter incremented atomically (committed on failure paths), `used_at` set on success (consumes token). Replay rejected via `used_at IS NOT NULL`. Wrong actor rejected via `ErrProofTokenWrongActor`. Exhausted rejected via `ErrProofTokenExhausted`.
- **Proof immutability** — `IsStageFinalized` + `ProofExistsForStage` checks prevent proof mutation after terminal stage. Service layer `ValidateProofForTransition` blocks transitions where mandatory proof is missing or stage already finalized.
- **Completion gating** — `EnsureProofForTransition` service method requires verified proof existence before allowing stage transitions that mandate proof (e.g. `delivering` for food/package).
