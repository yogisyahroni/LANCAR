# Evidence — COURIER-2026-001

## Acceptance Criteria Source

- `[x]` Profile separates identity, contact, market, home/operating zones, capabilities, vehicle and verification status.
- `[x]` Activation is server authoritative.
- `[x]` Required onboarding differs by market/service capability.

## Scope Implemented

- Added the canonical `DRAFT → SUBMITTED → VERIFYING → ACTIVE` lifecycle with
  `REJECTED`, `NEEDS_UPDATE`, `SUSPENDED`, and `DEACTIVATED` transitions.
- Added `courier_profile_status_history`, a database transition guard, and the
  `courier_profile_canonical` read model joining identity/contact, market,
  zones, vehicles, capabilities, and verification without duplicating their
  existing sources of truth.
- Normalized the historical `courier_profiles.status` ambiguity into
  `verification_status` plus an operational status projection, with an
  idempotent legacy backfill.
- Centralized market/channel/capability onboarding policy. On-demand, regular,
  food, and roadside/towing applications resolve different required documents
  and rules into an auditable checklist.
- Changed admin and auth activation paths to require a passed server-side
  checklist and a vehicle, then persist the authoritative state and user
  status transactionally.
- Updated courier matching, surge supply, SOS, tracking, retention, and
  analytics paths to use `onboarding_status = 'ACTIVE'` as the eligibility
  projection.
- Removed registration reads/writes to the non-existent legacy `couriers`
  table; registration now uses the canonical `users` + `courier_profiles`
  ownership boundary.
