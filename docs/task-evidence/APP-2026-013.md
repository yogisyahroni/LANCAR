# Evidence — APP-2026-013

## Acceptance Criteria Source

Original checklist from `task-food-marketplace-parity-2026.md`:

- `[x]` One backend experience service supports surface-specific schemas; do not force customer-home components onto courier/merchant.
- `[x]` Merchant can receive dynamic operational notice/campaign/help content without changing kitchen/order state logic.
- `[x]` Courier can receive dynamic safety/education/incentive/info modules without changing active-job state machine.
- `[x]` Customer Web and Android can share campaign id/eligibility while rendering native surface-appropriate components.

These are the original APP-2026-013 requirements. Staging deployment and interactive device validation are release follow-ups because they are not additional checklist requirements in this TASK-ID.

## Scope Implemented

- Extended the existing admin-service manifest contract with an explicit surface-to-component policy. Customer Android/Web retain the customer campaign component set; merchant/courier accept only operational, information and bounded campaign components.
- Added merchant Android manifest fetch with last-known-good persistence and a native operational content slot. It is mounted above existing merchant tabs and cannot change kitchen/order state.
- Added courier Android manifest fetch with last-known-good persistence and a native safety/education/incentive/info slot. It is mounted in the courier shell without changing `OrderViewModel`, duty state, active-job routing or proof transitions.
- Added a customer Web resolver client and native React renderer. The renderer carries the resolved manifest revision and campaign ID in the DOM, uses the same server audience resolution as customer Android, and only navigates through the existing customer route sanitizer.
- Reused the existing manifest checksum/revision, market/locale/app-version resolver and APP-2026-012 rollback/LKG ownership; no second config source or database table was created.
