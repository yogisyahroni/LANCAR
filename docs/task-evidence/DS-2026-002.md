# Evidence — DS-2026-002

## Acceptance Criteria Source

The original DS-2026-002 checklist in `task-food-marketplace-parity-2026.md` requires:

- [x] Token names describe role, not raw color, e.g. `color.action.primary`, `color.text.secondary`, `surface.raised`.
- [x] Light/Dark/System values map from one semantic contract.
- [x] Android/Web/Admin generated or manually synced values are testable against canonical token source.
- [x] Figma token naming maps one-to-one or through documented transform to code tokens.
- [x] Token validation includes WCAG protected pairs from Part S.
- [x] No service invents a new “primary green/orange” without design-system approval.

## Scope Implemented

- Added the canonical `design-tokens/tembus.tokens.json` source with TEMBUS semantic color roles, Light/Dark values, spacing, radius, typography, elevation, motion, size, content, Figma mapping metadata, and WCAG protected pairs.
- Added deterministic exporter outputs for Customer Web, Admin Web, and checked-in generated TypeScript token maps. CSS applications import the generated token CSS while retaining the existing semantic compatibility variables.
- Added `validate-tembus-design-tokens.mjs`, which validates required token families, every protected WCAG pair, CSS/Admin values, generated outputs, and Android Customer/Merchant/Courier mappings.
- Rebased the existing Part S color guard on the canonical TEMBUS source so CI no longer carries a second hardcoded color contract.
- Synchronized Android Customer, Merchant, and Courier semantic palette values and dark-mode `on-*` roles, including a separate dark primary/accent foreground where required for contrast.
- Added the canonical token validator to PR, staging, and production design-system workflow gates.
- Hardened audited Android decorative icon calls to use explicit empty descriptions, allowing the shared mobile accessibility source guard to pass without treating decorative icons as unlabeled interactive content.
