# Evidence — TOW-2026-006

## Scope Implemented

- The server now identifies towing orders from the persisted service code and maps status to explicit stages: `menuju_pickup`, `inspeksi`, `loading`, `perjalanan`, `unloading`, `selesai`, or `dibatalkan`.
- Towing tracking chooses pickup or destination as the active route target based on the authoritative stage and returns a towing-specific timeline alongside route/ETA data.
- Customer Android renders the towing timeline with human-readable stages and keeps the existing polling, socket-triggered refresh, last-known route, and stale-data messaging behavior.
- The Android tracking state now applies a monotonic stage policy so delayed polling/socket responses cannot replace a newer stage with an older one; terminal cancellation is protected as well.
- `TrackingResponse` carries the server stage/status used by the client recovery guard, and focused unit tests cover backward, equal/forward, and terminal snapshots.
- Existing location quality filters remain in force; invalid, spoofed, or stale courier locations are not exposed as the customer’s live location.
- Customer service tracking now keeps the pre-assignment state explicit: radar/search and map are visible while the server is searching, but service journey and provider contact are shown only after an accepted/assigned provider is present.
- Provider search timeout and radius behavior are loaded from the Admin-managed delivery service catalog; the customer tracking snapshot exposes the authoritative timeout/deadline state.
- Generic package/on-demand tracking also renders persisted pickup/drop-off markers when no courier GPS is available, so the search state is not a blank map.
- Roadside orders now require the customer to select and lock a nearby tambal ban/towing provider before order creation; the server rejects an unselected roadside provider.
- Courier-owned roadside offer inputs now persist service price, per-kilometre rate, toll entry, and toll exit in `courier_service_prices`; the customer quote uses those values and records the toll source as the provider offer.
- Customer roadside tracking hides journey, contact actions, and payment while searching/no-supply; after assignment it shows the provider, active map/route, journey, and persisted price breakdown.
- Tambal Ban now has one canonical customer entry flow: the Beranda tile opens the Figma-style emergency home, then vehicle selection, requested hole count, problem details, evidence, nearby offers, and booking. The towing shortcut returns to the canonical towing route picker; the legacy subtype route is retained only as a technical fallback and is not a second Beranda page.
- Customer hole scope is persisted in `orders.package_details.vehicle_details.requested_hole_count`; the driver app persists `price_per_hole_idr`, completed hole count, and calculated service total in the final report. Server validation rejects completion above the requested count, leaving extra holes outside TEMBUS as direct field negotiation.
- The customer note explaining that extra holes are handled directly with the technician is stored in `delivery_service_products.metadata.customer_note` and is returned by the report API, so both the request screen and final report avoid hardcoded policy text.
