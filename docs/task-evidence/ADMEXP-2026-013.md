# Evidence — ADMEXP-2026-013

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- [x] Admin sees estimated affected version distribution before hard update publish.
- [x] Hard update requires elevated permission + confirmation + reason + approval where configured.

- [x] Version policy is market/platform scoped; Android rule does not silently affect web/iOS/future surfaces.

## Scope Implemented

- Added a dedicated `/app-experience/version-policy` GUI entry backed by the existing protected Mobile Release Policies implementation. The legacy `/mobile-release-policies` route remains a compatibility alias, so there is one policy source of truth.
- Added explicit fields for latest, recommended and minimum versions, `none|soft|hard` mode, HTTPS store destination, effective start/end, active-order/support/new-transaction recovery flags, audit reason, and localized title/body. Existing body-only locale records remain readable with a safe fallback title.
- Added the Admin impact endpoint. It groups the last 30 days of scoped `event_outbox` experience telemetry by observed app version, marks versions below the proposed minimum, reports affected share and unknown-version events, and refuses to fabricate a user total.
- The GUI blocks hard publish when no observed sample exists, shows the version distribution, requires an explicit confirmation, and describes the recovery behavior before the mutation is sent.
- Hard mutation remains protected by the existing `experience.version_policy.write` capability, TOTP, idempotency key and audit reason. No separate maker-checker approval is configured for `mobile_release_policies`; the evidence does not claim one. Where approval is configured elsewhere in the experience control plane, that existing lifecycle remains authoritative.
- Backend schema and the existing database hard gate reject hard policies that disable active-order or support recovery, while hard mode holds new transactions. Unique market/client/platform scope and client/platform validation prevent an Android rule from affecting web or future surfaces.
- The conditional exempt/internal-cohort field is intentionally not exposed because no approved release-policy exemption is configured in this source of truth. Existing explicit cohort/canary controls remain in the App Experience control plane; no silent exemption is added to version policy.
