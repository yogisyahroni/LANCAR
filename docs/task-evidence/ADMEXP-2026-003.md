# Evidence — ADMEXP-2026-003

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- Every production-changing Admin button maps to an authenticated API operation; the browser does not write the database directly.
- Draft edit uses optimistic concurrency/revision/ETag so two admins cannot silently overwrite each other.
- Publish, rollback and kill-switch mutations are idempotent or protected against duplicate click/retry.
- Validation errors identify the exact field/component problem.
- Every mutation stores actor, role, market, surface, request ID, previous revision, new revision, reason and timestamp.
- API cannot publish a manifest while bypassing schema, permission or approval rules.

## Scope Implemented

- Completed the Admin Experience API contract in the existing bounded `admin-service`; no duplicate `experience-service` was created and the browser has no direct database path.
- Added authenticated lifecycle and collection routes for manifests, validation, preview, approval submit/approve/reject, publish, rollback, assets, revisions, audit, deep links, rollouts and kill switches.
- Added strong `If-Match` plus `X-Experience-Revision` draft preconditions under a manifest lock; stale writes return a typed `409 EXPERIENCE_VERSION_CONFLICT`.
- Applied TOTP and idempotency middleware to production-changing lifecycle/kill-switch mutations and made repeated state transitions safe to retry.
- Added structured `issues[]` responses with field/component paths for manifest, asset, deep-link and rollout validation.
- Added transactional audit metadata for actor role, request ID, market, surface, previous/new revision, reason, correlation ID and timestamp; audit rows remain append-only.
- Revalidated persisted canonical content and signature before publish, preserving existing schema, fallback, maker-checker and permission rules.
- Updated the dashboard draft save flow to send the current ETag/revision and fixed rollback/publish capability gating.
