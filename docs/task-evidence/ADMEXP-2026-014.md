# Evidence — ADMEXP-2026-014

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- [x] Preview resolves the same manifest schema/rules as production resolver, not a disconnected mock implementation.
- [x] Admin can compare `current live` vs `candidate revision` side-by-side/diff.
- [x] Unsupported component for selected old app version is visibly shown as skipped/fallback.
- [x] Broken asset/deep-link/contrast/schedule targeting appears as blocking validation before publish.
- [x] Preview never counts as real campaign impression/exposure metric.

## Scope Implemented

- Extended the existing `/admin/experience/manifests/:manifestId/preview` endpoint instead of creating a second resolver. Candidate selection uses the same `pickExperienceManifest`, semantic app-version range, locale, targeting and schedule rules as public resolution; localized content references use the existing resolver path.
- Added preview context selectors for surface/platform, market/country, locale, app version, schema capability, device-size preset, city, zone, new/existing profile, cohort and light/dark/system mode. The server validates and returns a sanitized context.
- Added a resolver result containing current live, candidate, fallback, section outcomes, changed fields/sections, validation issues and the selected context. The dashboard renders a live-versus-candidate comparison and actual section lists rather than treating local form rendering as production proof.
- Old app or schema capability is returned as `unsupported_app_version` or `unsupported_schema_version`; candidate sections are visibly marked `skipped` when no fallback exists or `fallback` when the current live revision is selected.
- Preview validation reuses persisted manifest integrity parsing. Invalid component properties, declared/missing assets, fallback cycles/kinds, deep-link values, design-token contrast, version/schedule constraints and targeting fallback requirements are surfaced as blocking issues. The publish button requires a fresh valid server preview; publish remains server-authoritative.
- The response explicitly contains `impression_recorded: false`, preview requests only create the existing audit action, and no campaign impression/exposure event is emitted by preview.
