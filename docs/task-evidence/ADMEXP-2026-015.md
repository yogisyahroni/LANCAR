# Evidence — ADMEXP-2026-015

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- [x] Save Draft never changes live user experience.
- [x] Submit Approval freezes candidate revision or creates an immutable candidate snapshot.
- [x] Approver sees diff, audience, schedule, rollout percentage, affected surfaces and risk/blast-radius summary.
- [x] Canary can target internal users or a small deterministic percentage before general release.
- [x] Percentage rollout supports staged increase without rebuilding manifest content.
- [x] Publish is atomic from the revision perspective.
- [x] Rollback selects an immutable known-good revision and records a reason.
- [x] The optional automated rollback guardrail can trigger on configured reliability thresholds with audit evidence.

## Scope Implemented

- Added an explicit editable `draft` approval status. Creating or editing a broad/high-impact campaign leaves it editable until the operator presses Submit Approval.
- Submit Approval transitions the candidate to `pending`; draft updates reject `pending` and `approved` candidates with `EXPERIENCE_APPROVAL_REVISION_LOCKED`, so the submitted revision cannot be changed under the approver.
- Approval remains maker-checker: the creator cannot approve, approval requires the submitted `pending` state, and publish requires `approved`.
- Added an approver-facing release summary to the server preview response: diff context, audience dimensions, schedule/timezone, rollout stage/percentage/cohort, affected surface and deterministic blast-radius level/reasons.
- Kept canary cohort filtering and stable authenticated-user percentage bucketing in the server resolver. The existing Duplicate-as-draft flow lets an operator promote percentage stages without rebuilding section content.
- Kept publish and rollback inside the existing manifest transaction/lock lifecycle. Historical payloads remain immutable; rollback requires an older historical revision and a non-empty reason.
- Preserved the existing runtime reliability guardrail. Reliability telemetry evaluates the current revision using a minimum sample and failure-rate threshold, records the rollback audit through the canonical rollback function, and returns the guardrail action to the telemetry caller.
