## Acceptance Criteria Source

Original checklist from `task-food-marketplace-parity-2026.md`:

- Backend can reorder/hide/show configured home sections without binary update.
- Service card visibility/order/subtitle/badge can be market/campaign targeted while actual service availability is revalidated by authoritative backend.

## Scope Implemented

- Added `DynamicHomeRenderer` with compiled native composables for hero banner, campaign strip, promo carousel, service grid, quick actions, info card, notice and spacer. No WebView, reflection, script execution or remote code path is used.
- Extended the existing experience-manifest control plane with safe `notice`/`spacer` components and service-grid `cards` entries containing only presentation `code`, `subtitle` and `badge` fields.
- Wired Dashboard to consume the process-wide APP-2026-002 snapshot. A non-empty manifest controls section order and content; an empty/packaged snapshot renders the existing packaged Gojek-style home grid.
- Intersected remote service-card configuration with the authoritative enabled-service response from `/api/v1/customer/delivery-services` before rendering or navigation. Existing booking flows remain responsible for final availability/eligibility truth.
- Added renderable-component filtering with an unknown-component telemetry event (`ExperienceRenderer`, `event=unknown_component`) and a testable telemetry sink contract.
- Preserved presentation-only boundaries in the backend schema; protected pricing, payment, order-state and authorization keys remain rejected.
