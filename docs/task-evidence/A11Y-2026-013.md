# Evidence — A11Y-2026-013

## Acceptance Criteria Source

- Use native semantic HTML/control first before custom ARIA recreation.
- Keep heading hierarchy meaningful.
- Make landmarks/navigation/main regions identifiable.
- Ensure accessible names of visible-label controls contain the visible label intent.
- Make status messages perceivable without forcing a focus jump.

## Scope Implemented

- The Customer and Admin full route inventories now enforce visible-label accessible-name matching for every visible interactive control.
- Decorative SVGs inside visible interactive controls must be explicitly hidden from assistive technology unless they provide an explicit semantic role/name.
- Visible `role="img"` graphics must expose an accessible name, and visible alert/status regions must expose non-empty accessible content.
- Each supported route now has an automated one-main/one-h1 contract, heading-skip check and named-navigation landmark check; chart/map regions with an accessible label must reference non-empty summary text. The full Customer/Admin inventory proves the heading hierarchy and navigation landmarks for all registered route/theme cases.
- Invalid controls with `aria-invalid="true"` must reference non-empty descriptive content; any `aria-sort` value must use the permitted vocabulary.

## Files Changed

- `frontend/e2e/accessibility.spec.ts` — Customer runtime semantic assertions.
- `admin-dashboard/e2e/accessibility.spec.ts` — Admin runtime semantic assertions.
- `frontend/src` and `admin-dashboard/src` — accessible labels/hidden decorative icons required by the inventory.
- `scripts/a11y/check-disabled-states.mjs` — source-level readability floor for disabled controls.
- `task-food-marketplace-parity-2026.md` — semantic checklist items for heading hierarchy and identifiable landmarks are checked from the full inventory; native-control and manual AT items remain open.
