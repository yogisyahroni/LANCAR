# Evidence — COURIER-2026-003

## Acceptance Criteria Source

- `[x]` Capability has status, evidence/certification, effective/expiry and market scope.
- `[x]` Matching always checks capability server-side.
- `[x]` UI shows why capability unavailable and remediation path.
- `[x]` Capability can be paused/suspended independently when appropriate.

## Scope Implemented

- Extended the existing `courier_service_capabilities` source of truth with
  certification type, private evidence storage key/checksum, certification and
  effective/expiry dates, market scope, and independent pause/suspension audit
  fields. Added a constrained status model, indexes, a server-side eligibility
  function, and an eligibility view exposing effective status, reason, and
  remediation path.
- Updated normal dispatch, preferred dispatch, offer acceptance, and broadcast
  targeting to call `courier_capability_is_eligible` with the courier market;
  client toggles cannot make an ineligible capability matchable.
- Added restricted admin capability updates with role/TOTP protection,
  validation for dates, evidence keys, checksums, market scope, suspension
  reasons, and status transitions. Admin/mobile capability responses now expose
  certification metadata and derived availability fields.
- Updated the Android courier model and all relevant service/profile/offer
  surfaces to consume server eligibility, show why a capability is unavailable,
  and show the remediation path. The app never uses a local toggle as the
  server-side eligibility source.
- Corrected the observability guard false positive for route registry keys that
  were lexically close to a log call; the guard now passes against the complete
  repository.
