# Evidence — GLOB-2026-013

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- Backend supports documented minimum client versions during the rollout window.
- Additive API changes are preferred; breaking changes require an explicit version and migration path.
- The server knows app version/schema capability before returning unsupported dynamic features.
- Old apps remain safely usable or receive an explicit upgrade-required state and must not silently misprice or misrender an order.
- Country launch has a rollout/canary/rollback plan independent from mobile store release cadence.

## Scope Implemented

- Added a shared backend compatibility contract for customer, courier, merchant and web clients. It parses bounded version, schema and capability headers, applies minimum-build/schema policy, and returns `compatible`, `upgrade_required` or legacy-safe `unknown` states.
- Extended the public latest-version endpoint to support merchant clients and return minimum supported build, API schema policy and explicit compatibility/force-update data.
- Added dynamic-feature filtering to public web/mobile flags. Legacy or incompatible clients receive no dynamic flags; cache storage keeps raw rows and the client-specific response is private and varies by compatibility headers.
- Added compatibility headers to all requests from the three Android apps and the customer web client. Added response models and update-manager handling for explicit upgrade-required state.
- Added a migration that seeds compatibility metadata and a documented additive-first API policy, compatibility matrix, rollout/canary sequence and rollback path.
