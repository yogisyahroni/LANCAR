# Evidence — ADMEXP-2026-002

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- Market scope and surface scope enforced server-side.
- An Indonesia admin cannot mutate Singapore/Malaysia/global configuration without explicit global scope.
- Global/high-blast-radius publish supports maker-checker/two-person approval.
- A maker cannot approve their own revision where maker-checker is required.
- Kill-switch permissions are narrower than ordinary marketing edit permission.
- Every denied action returns a typed reason and is auditable.

## Scope Implemented

- Extended the existing centralized `permissions` / `role_permissions` model with all 12 `experience.*` capabilities from the blueprint.
- Added explicit role and user scope grants for market and surface. `ops_admin` is seeded to `id-jk/*`; `super_admin` and `ops_security` receive explicit `*/*` grants. Global scope is therefore a database grant, not a role-name bypass.
- Replaced Experience and shared feature-flag/release-policy role-only gates with a fail-closed backend authorization middleware that checks capability plus target market/surface.
- Draft updates validate both the current manifest scope and the requested new scope, preventing an operator from moving an in-scope draft into an unassigned market.
- Global feature-flag actions require an explicit global scope. Feature-flag write is restricted to `super_admin`; kill-switch execution is separately permissioned and is not granted to ordinary `ops_admin` draft editors.
- Preserved the existing service-level maker-checker invariant: broad/high-impact manifests require approval, and the creator cannot approve the same revision.
- Returned structured denial responses with `code`, `reason_code`, capability, target scope and correlation/request identifiers; denied actions are written to the existing append-only `audit_logs` table for real UUID-authenticated actors and also emit redacted structured security logs.
- Added the same capability list to the Admin session response so the dashboard filters navigation and mutation controls using server-issued permissions rather than a duplicated role matrix.
