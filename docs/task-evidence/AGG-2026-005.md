# Evidence — AGG-2026-005

## Scope Implemented

- Bulk jobs now store and preserve the owning customer ID through upload, async progress, validation, and completion.
- Status, row editing, row deletion, and processing endpoints return not-found for a different customer instead of exposing another customer's job.
- Review mutations increment a job revision; processing requires the exact reviewed revision and refuses stale data.
- Bulk processing now requires an idempotency key, persists created order IDs/result in Redis, and replays the stored process result on resume instead of creating duplicate child orders.
- The bulk page restores a pending job after refresh; an in-progress job resumes polling and a processed job returns to order history.
- Static default pickup coordinates were removed from the bulk upload UI; upload requires an actual selected location.
- Process failures are represented as a failed job state rather than silently leaving an upload in limbo.

## Files Changed

- `backend/admin-service/src/controllers/bulkOrder.controller.ts` — owner scoping, revision, process replay, durable result, and async failure state.
- `backend/admin-service/src/routes/order.routes.ts` — idempotency middleware for bulk process/pay routes.
- `backend/admin-service/src/bulkOrderSafety.test.ts` — owner isolation and processed-job replay tests.
- `frontend/src/app/(portal)/orders/bulk/page.tsx` — server-backed refresh recovery.
- `frontend/src/components/orders/bulk/UploadStep.tsx` — real pickup-coordinate requirement and resumed polling.
- `frontend/src/components/orders/bulk/PaymentStep.tsx` — exact job revision/idempotency request and no fabricated payment success.
- `frontend/src/components/orders/AggregatorWizard.tsx` — inline bulk process sends revision and idempotency key.
