# Evidence — APP-2026-015

## Acceptance Criteria Source

The original checklist in `task-food-marketplace-parity-2026.md` requires:

- `[x]` Soft update is dismissible and never impersonates transaction failure.
- `[x]` Hard update only used when old binary is genuinely unsafe/incompatible.
- `[x]` Active order/support access strategy is defined before hard-blocking an old app.
- `[x]` Version rule is market/platform scoped.
- `[x]` Remote config is not used as a way to avoid required store review for new native capability/code.

## Scope Implemented

- Added `mobile_release_policies` and append-only `mobile_release_policy_audit`, scoped by market, client type, and platform. The database constraints reject invalid version ordering, invalid hard reasons, and hard policies that remove active-order/support recovery access.
- Added backend read/decision/upsert logic and extended `GET /api/v1/system/latest-version` with localized policy decisions, soft/hard state, recovery access, store destinations, cache variance, and compatibility metadata. A client below the market minimum is treated as incompatible and hard-gated even when the authored policy is soft.
- Added protected Admin Dashboard management with role, TOTP, idempotency, audit reason, HTTPS store destination, localized messages, and an explicit release-metadata-only boundary.
- Updated customer, courier, and merchant Android response models, update managers, and dialogs. Soft prompts expose a dismiss action; hard prompts expose the unsafe/incompatible reason and active-order/support/new-transaction recovery strategy.
- Added the operational contract in `docs/release/mobile-update-policy.md`; it explicitly keeps native capability changes subject to normal reviewed store releases.
