# Evidence — GLOB-2026-001

## Acceptance Criteria Source

Original checklist requirements from `task-food-marketplace-parity-2026.md`:

- `[x]` Every market has canonical ISO country/region code, currency, default locale, timezone, measurement system, phone/address rules and launch state.
- `[x]` Service availability is config-as-data per market/city; do not fork code for a country.
- `[x]` Payment methods, logistics providers, map providers, tax policy references, insurance policy references and service hours are market scoped.
- `[x]` Legal/privacy/terms document version and effective date are market scoped and auditable.
- `[x]` Market config has version, effective-from, rollback version, actor and approval audit.
- `[x]` Clients receive only public market config; credentials/secrets remain server-side.
- `[x]` Unknown market or incomplete config fails closed for transactional features rather than falling back to Indonesia assumptions.

## Scope Implemented

- Evolved the existing `admin-service` configuration ownership boundary rather than creating a duplicate platform-config service.
- Added canonical `market_configs`, market/city/service availability, legal document, append-only audit, and database readiness structures in migration `20260908000020_global_market_configuration.sql`.
- Added validated admin CRUD/update/approval services and routes. Material changes increment the version, retain the previous version as rollback metadata, reset approval, and write an audit event. Activation requires readiness and the existing TOTP/RBAC controls.
- Added a read-only public market resolver. It requires an explicit `market_code`, returns only public capability/policy fields, and returns `404` for unknown markets or `503` with reason codes for incomplete markets. No Indonesia fallback is used.
- Added the gateway public auth policy and proxy route, plus an admin dashboard control plane for canonical fields, effective scheduling, availability, legal documents, readiness, and approval.
- Provider capability references accept only public identifiers/strict reference objects; credential-shaped fields such as `api_key` are rejected at the service boundary.
