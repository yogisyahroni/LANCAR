## Scope Implemented

- On-demand customer order creation now sends a stable `X-Idempotency-Key`, validates `success === true`, and requires a non-empty persisted server order id before any success path.
- A timeout or transport-level unknown outcome is surfaced as pending/retry. The key and a non-PII payload fingerprint are retained in session storage so a retry can replay the same request; an idempotency-in-progress response is also treated as retryable.
- A successful create response is stored with its order id before payment initialization. Refresh/retry can reconcile that order through the authenticated server detail endpoint instead of creating another order.
- Payment-session initialization has the same server-response validation and stable per-order idempotency key. Payment success is only emitted after the server-owned payment check reports `paid`; pending state has an explicit status-retry action.
- Aggregator helper code now reuses the shared idempotency-key generator without changing its server contract.
