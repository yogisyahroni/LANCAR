# Support Cases Contract — GLOB-2026-010

## Ownership

`admin-service` owns the support case workflow because it already owns the
admin, dispute, exception and operational support boundary. A separate
microservice would duplicate authentication, database access and operations
ownership without adding an isolation boundary.

## API

- `POST /api/v1/support/cases` — authenticated customer, merchant, courier or staff intake.
- `GET /api/v1/support/cases` — authenticated actor's cases; support staff can see the queue.
- `GET /api/v1/support/cases/:id` — actor-scoped detail or support-staff detail.
- `GET /api/v1/admin/support/cases` — support queue for the admin console.
- `PATCH /api/v1/admin/support/cases/:id` — status, SLA, owner and escalation updates.
- `POST /api/v1/admin/support/cases/:id/actions` — policy-gated actions with idempotency.

Gateway routes use the `web-session-or-jwt` policy and forward to admin-service.
Cookie-authenticated mutations retain the existing CSRF protection.

## State and references

Cases keep references to authoritative order, payment, refund, courier,
merchant, carrier, proof, claim and reconciliation records. They do not copy
those records' state. The detail API resolves current order/payment state for
policy evaluation at read/action time.

All lifecycle events are append-only in `support_case_events` and are also
published to the existing event outbox. SLA due time, assignment, escalation,
resolution and reopen count are first-class fields.

## Action safety

Suggested/allowed actions are generated by the versioned policy service using
service, market, category, case status, order status and payment status.
Refund/compensation actions require a finance role and TOTP, create a durable
processing action before the call, send an idempotency key to order-service, and
record only a redacted success/failure result after the audited financial API
responds. Support never writes `payments`, `refunds` or ledger tables directly.

## Privacy

Payment and proof references are restricted to finance/security roles. Customer
responses omit staff actor IDs and action idempotency keys. Descriptions and
notes redact payment-like references and secrets before persistence.
